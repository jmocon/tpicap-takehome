# AI Usage Report

## Tools used

**Claude Code** (Sonnet 5, later Opus 5), used as the primary and only development tool for this exercise — no other AI coding assistant was used. Planning, implementation (backend, frontend, Docker, CI, tests) and the deliverable documents were all produced through it, across several working sessions rather than one sitting.

A deliberate part of the setup: the repo carries its own **project subagents** in `.claude/agents/` — `backend-engineer`, `frontend-engineer`, `devops-engineer`, `qa-engineer`, `ux-reviewer` — each a scoped rulebook stating what it owns, what it must not touch, and how it verifies its own work. Later features were built by delegating to the role that owned the relevant file tree, with review passes run by the two read-only roles. `.claude/docs/agent-team-workflow.md` documents when to parallelize (disjoint file trees) versus amend work already in flight (shared files), which is what kept concurrent agents from clobbering each other.

## How it was used

The work happened in four distinct phases:

1. **Planning, interactively, over many small turns.** Before any code was written, the assessment PDF was fed in and Claude was asked to turn it into working documents: `CLAUDE.md` plus a `.claude/docs/` folder (spec extraction, deliverables/grading breakdown, a proposed folder structure, a progress checklist, and a list of things only a human could do — accounts, `git`/Docker issues on this machine, etc.). The folder structure in particular went through several rounds of pushback before implementation started: questioning why `realtime/` was split from `trades/`, whether `features/` was the right name when there was nowhere for "pages," why tests weren't colocated with the files they test, and whether `trade-blotter`/`trade-form` should follow Atomic Design. Each round, Claude explained the reasoning and the doc was revised or the reasoning was accepted before moving on.
2. **Autonomous build, in the background.** Once the plan was solid, Claude was told to build the entire app end-to-end without further check-ins (the session owner was stepping away), make the remaining implementation-level calls itself, and leave a clear log of every decision for review. It scaffolded `backend/` and `frontend/`, wrote all source files, installed dependencies, ran the test suites and builds, fixed the failures it hit along the way, wrote Dockerfiles and `docker-compose.yml`, generated the seed-data samples, wrote the README, and finally ran a self-review pass (`/simplify`, four parallel review agents each focused on one angle — reuse, simplification, efficiency, altitude) against its own output and applied the fixes.
3. **Follow-up session: git setup, UX/demo work, and agent tooling.** A later session pushed the built app to GitHub (fixing a `.gitignore` gap that would have committed `node_modules` in the process), applied a user-supplied UX-psychology reference document selectively (see below), built a client-side trade analytics panel and two live-demo controls ("Simulate Trade", "Auto Simulate"), and set up project subagents (`backend-engineer`, `frontend-engineer`, `devops-engineer`, `qa-engineer`) plus an agent-team workflow doc — surfacing along the way that this environment's `Agent` tool doesn't actually support the documented agent-teams feature (see below).
4. **Feature expansion and a pre-submission audit.** Client-side routing and a per-symbol page (OHLC candlesticks derived from individual executions, since the data model has no candle data), substring search with a suggestion dropdown, per-row sparklines, then all four bonus features — audit trail, position summary, FIFO P&L, and authentication — designed up front in plan mode at the user's explicit request for architectural rigour, then implemented as three sequenced passes with independent verification between each. Finally a GitHub Actions CI pipeline, and a full audit run through the repo's own `qa-engineer` and `ux-reviewer` agents, which surfaced container-only bugs (a route collision and a missing SPA fallback) that no test suite would have caught.

## Key decisions influenced by AI

- **`node:sqlite` over `better-sqlite3`**: Claude's own call, verified experimentally (checked the installed Node version supports it without flags) before committing, specifically because the brief requires the app to run on Windows/Linux/Mac and `better-sqlite3`'s native compilation step is a real cross-platform risk that a zero-dependency built-in module avoids entirely.
- **Consolidating `CreateTradeForm`/`AmendTradeForm` into one `TradeForm`**: the originally planned folder structure had two separate form files; while implementing, Claude recognized they'd be near-identical and merged them into one component parametrized by an optional `initialTrade` prop, then updated the planning doc to match reality rather than leaving it stale.
- **Vitest over Jest** for both frontend and backend, and upgrading `vitest`/`vite` mid-build after the initially-installed versions (vitest 2.1.9 / vite 5.4.21) failed to resolve `node:sqlite` at all — Claude diagnosed this as the bundled vite-node's builtin-module allowlist predating that API, and fixed it by upgrading rather than working around it with a config hack.
- **FIFO lot-matching for P&L, with an explicitly labelled proxy for "last price".** The brief asks for a P&L view but the data model has only executions — no market data and no closing prices. Rather than inventing a number, Claude proposed FIFO matching (each closing trade against the oldest open lot, so a long→short flip falls out naturally with no special case) for *realized* P&L, and marked *unrealized* P&L against the symbol's most recent trade price as a documented stand-in for a real mark. Both the methodology and its limitation are written into the README rather than left implicit, because a P&L number whose derivation isn't stated is worse than no P&L number.
- **Auth scoped to a login gate, not authorization.** The brief says "simple login capability"; Claude deliberately did not add per-user ownership rules ("only the booking trader may amend"), since that's a different and much larger feature. Related: `node:crypto`'s `scrypt` for password hashing instead of `bcrypt`, keeping the zero-native-dependency property that motivated `node:sqlite` in the first place.
- **An `AuditLogger` interface mirroring the existing `Broadcaster` seam.** Rather than having the service write audit rows directly, Claude reused the pattern already proven in this codebase, so the audit trail is injectable and the service stays unit-testable without a database writer. The field-diff itself was extracted as a pure function so the trickiest part is testable in isolation — the same reasoning applied to the FIFO engine.
- **Verification discipline that caught real bugs.** Every delegated piece of work was independently re-verified rather than trusted: re-running the suites, reading the diffs, and hand-tracing the arithmetic. That caught `aggregateOHLC` silently including cancelled trades (so a cancelled bad print could set a candle's high), and — during a Docker review — that an nginx route Claude itself had added collided with a same-named SPA route, making the positions page unreachable in containers. Neither was caught by tests.

## Where AI-generated suggestions were accepted or rejected

**Accepted, after pushback that improved the result:**
- Folding two form components into one (see above) — accepted as a better design once flagged.
- Moving from a mirrored `test/` directory to colocated `*.test.ts` files, and splitting `pages/` out of `features/` — both were direct user corrections to Claude's first draft, both accepted and applied.
- All four `/simplify` findings that were genuine duplication or waste (shared SQL/ID-generation helpers, a single `UPDATE ... RETURNING` instead of three separate queries per amend/cancel, dropping an unnecessary repository test-double interface in favor of testing against a real in-memory DB) were accepted and applied.

**Rejected / consciously not applied**, each with a stated reason rather than silently ignored:
- Full Atomic Design methodology for `components/` — rejected because it has no natural home for the hooks and validation logic that live alongside a feature's components; a lighter `components/ui/` split was offered as a middle ground but ultimately left flat since a two-screen app doesn't yet have enough shared primitives to justify it.
- `/simplify`'s suggestion to add `React.memo`/`useCallback` throughout the trade table and page — rejected as premature optimization at this app's scale (a non-virtualized ~300-row table re-renders about the same either way).
- `/simplify`'s suggestion to unify the frontend's hand-written form validation with the backend's zod schemas — rejected because they run in different runtimes and the backend is meant to be the actual integrity boundary regardless of what the client does; documented as an intentional trade-off in the README rather than "fixed."
- Sharing `Trade`/event types between frontend and backend via a monorepo package — considered and explicitly rejected as unnecessary overhead for this exercise's scope; documented as an accepted trade-off (manual sync) in the README instead.
- **A supplied 18-principle UX document was applied selectively, not wholesale.** Roughly half of it was consumer growth-hacking (progress meters padded to start above zero, loss-aversion framing on cancellation, variable-reward loops, decoy pricing tiers). Claude flagged those as dark patterns unsuited to an institutional trading tool *before* writing any code and applied only the legitimate usability principles — button/data hierarchy, proximity grouping, progressive disclosure. The `ux-reviewer` agent later added to this repo carries that exclusion forward explicitly, so the rejection is durable rather than a one-off judgement.
- **A "team-lead" orchestrator agent was proposed and argued against.** It would have run once, dispatched, and had no way to wait on asynchronous completions and react — which is precisely the lead's job. The four-step workflow the request was really after (split → dispatch or amend-in-flight → verify-don't-trust → review-against-docs) was written into `.claude/docs/agent-team-workflow.md` as a standing procedure instead, with the session itself remaining the lead.

**Where Claude was wrong, and it mattered:**
- A chart-height cap (`max-height: 20vh`) was applied globally instead of scoped to the multi-column dashboard, which letterboxed the full-width stacked charts — they rendered at roughly half width with ~8px axis labels. Caught by the `ux-reviewer` agent, not by tests.
- An nginx `location /positions` block added to fix Docker login created a collision with the SPA route of the same name, making the positions page unreachable in containers. Caught by the `qa-engineer` agent. The fix was structural — prefix the whole API under `/api` — rather than another per-route special case.
- An empty-state string was edited without re-running the test suite (only the type-checker), breaking a test that asserted the old copy. Caught by the next agent to run the full suite. The lesson — type-check is not verification — was applied consistently afterwards.
